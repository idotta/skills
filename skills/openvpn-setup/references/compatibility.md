# Legacy .ovpn directives on OpenVPN 2.6 / OpenSSL 3

Most `.ovpn` files were generated by an appliance whose export template predates OpenVPN
2.5. The directives below still *parse*, so the config looks fine, but they either no
longer do what they used to or are actively rejected. The errors are misleading, which is
why they're worth recognizing on sight.

## Quick table

| Directive in profile | Symptom | Fix |
|---|---|---|
| `cipher X` with no `data-ciphers` | `AUTH_FAILED,Data channel cipher negotiation failed (no shared cipher)` | Add a broad `data-ciphers` list |
| `comp-lzo` / `compress lzo` | Connects, then no traffic; or `Compression is not allowed` | `allow-compression yes` |
| Old CA, SHA1 signatures | `certificate signature failure`, `ca md too weak` | `tls-cert-profile insecure` |
| `BF-CBC`, other legacy ciphers | `Cipher not supported` / unavailable | `providers legacy default` |
| `tls-auth` with no `key-direction` | `Initial packet ... bad HMAC` / silent timeout | `key-direction 1` |
| `ncp-disable` | Warning, ignored | Delete it |
| `keysize`, `tun-mtu-extra` | `Unrecognized option` (fatal in 2.6) | Delete them |

## The cipher trap

Worth its own section because it is the most common failure and the least intuitive.

Before OpenVPN 2.4, `cipher AES-256-CBC` set the data-channel cipher outright. From 2.4
onward, ciphers are *negotiated* — the client advertises a `data-ciphers` list and the
server picks. In 2.6 the standalone `cipher` directive is only a fallback.

A stale profile therefore advertises nothing useful. If the server has since moved to GCM
(most have — UniFi, pfSense, and OPNsense all default to `AES-256-GCM` now), negotiation
finds no overlap and the server rejects the session.

It reports this as:

```
AUTH: Received control message: AUTH_FAILED,Data channel cipher negotiation failed (no shared cipher)
```

The `AUTH_FAILED` prefix is the problem. Users see it, conclude their password is wrong,
and go reset credentials that were never the issue. **Read the text after `AUTH_FAILED`
before concluding anything about credentials.** Note also that the TLS handshake fully
succeeded before this point — if you saw `Peer Connection Initiated`, the certs and
tls-auth key are all correct.

The fix is to offer a list wide enough that any plausible server finds a match:

```
data-ciphers AES-256-GCM:AES-128-GCM:CHACHA20-POLY1305:AES-256-CBC:AES-128-CBC
data-ciphers-fallback AES-256-CBC
```

Resist pinning to a single cipher. You generally don't know what the server supports, and
pinning is what caused the problem in the first place. After connecting, the log's
`Data Channel:` line reports what was actually negotiated — that's your ground truth.

## Compression

OpenVPN 2.6 disables compression by default because of the CRIME/VORACLE class of attacks,
where compressing attacker-influenced plaintext alongside secrets leaks information.

If the server requires `comp-lzo`, the client has no way to opt out and still connect. Add
`allow-compression yes` and mention the tradeoff once — it's real but modest for a tunnel
carrying internal traffic, and it's the server operator's decision, not something the
client can fix. If the user controls the server, disabling compression there is the actual
remedy.

Two warnings appear and can be ignored: the compression warning itself, and a note that
data channel offload (DCO) is disabled — kernel offload is incompatible with compression
anyway, which costs some throughput but nothing functional.

## OpenSSL 3 certificate policy

OpenSSL 3 enforces a minimum security level that rejects SHA1 signatures and short keys.
Many appliance CAs, especially ones generated years ago and valid for 15 years, fall below
it.

```
tls-cert-profile insecure
providers legacy default
```

`insecure` here means "accept the security level this CA was built with", not "skip
verification" — the certificate chain is still fully validated. Add these when you see
certificate rejections; they're harmless when unnecessary.

Note that `auth SHA1` is unrelated to this. That's the HMAC for the tls-auth control
channel and works fine on modern OpenSSL.

## Reading the handshake

The log tells you how far you got. Each stage clears a different class of problem:

```
TCP connection established              → network path OK
VERIFY OK: depth=1 ... CN=...CA         → CA trusted
VERIFY OK: depth=0 ... CN=...Server     → server cert valid
Control Channel: TLSv1.3, cipher ...    → TLS up, tls-auth key correct
Peer Connection Initiated               → control channel fully established
PUSH_REPLY, ...                         → server accepted the client
Initialization Sequence Completed       → tunnel up
Data Channel: cipher 'AES-256-GCM'      → what was actually negotiated
```

Anything failing *after* `Peer Connection Initiated` is a data-channel or policy problem,
not certificates and not TLS. That distinction saves a lot of misdirected debugging.

## Reading PUSH_REPLY

The `PUSH_REPLY` line is the server telling you how the tunnel should be configured, and
it's the authoritative list to verify against later:

```
PUSH_REPLY,dhcp-option DNS 192.168.0.2,route 192.168.0.0 255.255.255.0,
route 172.16.50.0 255.255.255.0,route-gateway 10.50.0.1,topology subnet,
ifconfig 10.50.0.2 255.255.255.0,peer-id 0,cipher AES-256-GCM
```

- `route ...` — subnets that should reach the tunnel. Count them; verify the same count
  appears in `ip route show dev tun0`.
- `dhcp-option DNS ...` — DNS servers the server wants used. Raw OpenVPN accepts and then
  ignores these; see the DNS section of `networkmanager.md`.
- `ifconfig` / `route-gateway` — your tunnel address and its gateway.
- `redirect-gateway` — if present, all traffic is being routed through the VPN.
